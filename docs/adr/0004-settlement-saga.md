# ADR-0004: Сага расчётов — оркестрация с sync-фасадами и протоколом decide → effect → commit

Статус: принят (2026-06-11). Связан: ARCHITECTURE.md §6 (целиком), §2.4, §3.1; BOOK_AUDIT.md правило 38.
Это ADR с явным трейдоффом «sync-фасады vs all-async» (графт Д2/Д3) — решение аудируемо, условия пересмотра внизу.

## Контекст

После молотка процесс пересекает контексты: счёт победителю (billing), оплата/таймаут/отказ от оферты,
компенсации — second chance для runner-up, перевыставление лота, провал продажи (auction). Входы саги —
at-least-once события четырёх видов + HTTP-команда `DeclineSecondChanceOffer`; на каждом шаге саге нужен
**результат** команды другому контексту до перехода состояния. Ретраи и крахи между side effect-ом и commit-ом
состояния саги неизбежны.

## Решение

**Оркестрация**: process manager `Settlement` — богатый агрегат-state-machine в Postgres
(`Started | AwaitingPayment | AwardingRunnerUp | SecondChancePayment | Settled | Relisted | FailedUnsold`);
решение компенсации (`NextStep`) — чистая функция домена саги. Полная таблица переходов — ARCHITECTURE.md §6.3.

**Команды другим контекстам — синхронные**, через consumer-defined интерфейсы `auctionGateway`/`billingGateway`
→ адаптеры → фасады `service/`. Обоснование: шаг саги синхронен по природе — без результата `IssueInvoice` или
`AwardToRunnerUp` переход состояния бессмыслен; in-process вызов дёшев и попадает в тот же трейс.

**Протокол шага (фикс транзакционной структуры): decide → effect → commit.**

1. *decide* — короткое чтение + чистая доменная функция решения; «состояние уже дальше» → ack (дубликат).
2. *effect* — gateway-вызовы **строго вне какой-либо транзакции settlement** (никогда внутри updateFn:
   иначе чужая транзакция коммитится под row-lock-ом саги). Каждый фасад идемпотентен:
   «уже в целевом состоянии» → sentinel → no-op.
3. *commit* — короткая `repo.Update` (FOR UPDATE + version): переход state machine. Конфликт → ack,
   эффекты были идемпотентны.

Любой crash между фазами восстанавливается redelivery-ем (idempotent continuation); карта швов и
тест-обязательства — §6.7. Премативные события (WinnerReassignedV1 раньше commit-а AwardingRunnerUp) —
**fast-forward**: событие само есть доказательство совершённого effect-а (§6.3).

**Три слоя идемпотентности** (каждый — отдельный тест): state-machine guard-ы; детерминированные UUID
(`uuidv5(auctionID+":"+attempt)` для инвойсов, `uuidv5(nsRelist, auctionID)` для relist);
UNIQUE-constraints (`(auction_id, attempt)`, `UNIQUE(relist_of)`).

**Таймер один и не в саге**: `due_at` — инвариант Invoice (billing), expiry-воркер там же; сага не спит и
не хранит дедлайнов. Гонка Paid vs Expired vs Declined разрешается на агрегате Invoice (row lock +
guard-таблица §2.2) — сага никогда не видит конфликтных сигналов; проигравшая оплата компенсируется
PSP Refund-ом (§3.1).

## Трейдофф sync-фасады vs all-async (контраргументы Д2/Д3 — учтены)

- Д2 («чистый async»: команды-события + reply-события): + нет цикла settlement→auction, равномерная модель
  доставки; − удваивает число событий и контрактов, идемпотентность размазывается по парам команда/ответ,
  трейс и отладка дробятся. Отклонено для MVP.
- Д3 («отказ от цикла»): цикл settlement→auction смягчён переносом знаний в данные: события несут
  `RunnerUpQualifies` (резерв скрыт), `NextStep` живёт в домене саги; auction не знает о существовании саги —
  только фасадные команды с доменной семантикой.

**Условия пересмотра** (любое — повод вернуться к async-командам): вынос auction или billing в отдельный
сервис (фасад → gRPC сохраняет протокол, но сетевые ретраи меняют экономику); рост числа шагов > ~6;
видимая в `molot_saga_transitions_total` / latency-метриках деградация фасадных вызовов.

## Последствия

- (+) Состояние процесса наблюдаемо одним SELECT (`SettlementStatus`, ops); компенсации — бизнес-операции
  (second chance / relist / fail), не технический rollback; ни один crash-шов не теряет и не дублирует эффекты.
- (−) Протокол требует дисциплины «все фасады идемпотентны» — закреплено таблицей §2.1/§6.6 и тестами швов.
- (−) Settlement знает о фасадах двух контекстов — принятая цена оркестрации (см. трейдофф).

## Альтернативы

- **Хореография без process manager** — отклонено: ветвящиеся компенсации размазываются по подписчикам,
  нет единого состояния для ops, cap relist-ов негде держать.
- **All-async команды-события** — отклонено для MVP (см. трейдофф), путь миграции сохранён.
- **Распределённая транзакция через две схемы** — отклонено: ломает границы контекстов (правило 3).
