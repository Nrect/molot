# ADR-0003: Граница агрегата Auction — история ставок в границе согласованности, но не в памяти

Статус: принят (2026-06-11). Связан: ARCHITECTURE.md §2.1, §5, §7; BOOK_AUDIT.md §3–4.

## Контекст

История ставок «горячего» аукциона не ограничена (тысячи строк), а все инварианты ставки зависят только от
«головы» состояния: минимум = текущая+шаг, самоперебитие, продавец не ставит, порог верификации, анти-снайп-окно.
Загружать всю историю в агрегат — O(n) память и рост contention; выносить ставки в отдельный агрегат — терять
атомарность инварианта «ставка против актуального окна/лидера». Саге дополнительно нужен runner-up
(second chance), а резервная цена не должна утекать наружу.

## Решение

- Полная история ставок входит в **границу согласованности** (пишется в той же транзакции), но **не загружается
  в память**. Агрегат хранит топ-2 денормализованно: `leadingBid`, `runnerUpBid` (+ `bidCount`).
- `PlaceBid` — единственная точка инварианта: каскад guard-ов фиксированного порядка, затем атомарно
  runnerUp←leading, leading←новая Bid, анти-снайп-продление окна. Возвращает принятую `Bid`.
- Репозиторий в одной транзакции: append в `auction_bids` (append-only, никогда UPDATE) + UPDATE snapshot-строки
  `auctions` с `version+1` (`SELECT ... FOR UPDATE` + optimistic version — belt-and-suspenders).
- Чтение истории — забота read-стороны: query `BidHistory` ходит прямо в `auction_bids` (отдельная проекция
  была бы кодом «на будущее»).
- **Снапшот политик при листинге** (графт Д2): `verifyAbove` и `AntiSnipePolicy` снимаются с конфига один раз
  в `New(...)` и хранятся в агрегате — правила лота детерминированы во времени, смена платформенной политики
  не меняет идущие аукционы; `PlaceBid` конфиг не читает.
- Резерв скрыт всегда: события и API несут только производные (`HasReserve`, `RunnerUpQualifies` —
  готовый bool для саги, посчитанный в `Close`).
- Идемпотентность фасадных команд саги — на агрегате: маркеры `winnerReassigned`/`settled`/`outcome`,
  sentinel «уже в целевом состоянии» → no-op; `WinnerReassigned` записывается ровно один раз — транзакцией,
  совершившей переход (семантика — таблица в §2.1).

## Последствия

- (+) Загрузка агрегата O(1); optimistic locking по одной маленькой строке; история любого размера не влияет
  ни на латентность ставки, ни на contention.
- (+) Гонка PlaceBid vs Close сериализуется row-lock-ом той же строки (механика закрытия — ARCHITECTURE.md §10);
  это сердце системы, закрыто обязательными race-тестами.
- (−) Денормализация топ-2 — дублирование данных лога; принято: snapshot восстановим из `auction_bids` при нужде.
- (−) `auction_bids` пишется и write-, и read-путём — задокументировано как осознанное прямое чтение
  write-таблиц (правило «не всякому query нужен read model»).

## Альтернативы

- **Все ставки в памяти агрегата** — отклонено: память/contention растут с историей.
- **Bid как отдельный агрегат** — отклонено: инвариант «ставка против актуального окна и лидера» требует
  одной транзакции и одного лока.
- **Event sourcing для Auction** — отклонено на MVP: добавляет инфраструктуру и кривую обучения;
  append-only лог ставок уже даёт аудит, переход возможен позже за тем же Repository-интерфейсом.
