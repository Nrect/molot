# Хайлоад: паттерны-мастхэв

> База, без которой система под нагрузкой не живёт. Формат: суть → когда нужно → главная ловушка → как ложится на Molot. Порядок = порядок реальных узких мест: БД → кэш → очереди → защита от перегрузки → масштабирование → сеть → наблюдаемость → Go-специфика.

---

## 1. Данные — первое и главное узкое место

### 1.1 Connection pooling (PgBouncer)
**Суть:** Postgres дорого платит за каждое соединение (процесс на коннект); пулер в transaction-режиме мультиплексирует тысячи клиентских коннектов в десятки серверных.
**Когда:** >2-3 инстансов приложения или >100 коннектов суммарно.
**Ловушка:** transaction pooling ломает session-уровневые фичи (prepared statements по имени, advisory locks session-scope, LISTEN/NOTIFY). pgx в режиме `QueryExecModeCacheDescribe`/simple protocol — совместим.
**Molot:** пулы уже капнуты (MaxOpen=MaxIdle=30); PgBouncer встаёт между app и PG без изменения кода, но проверить watermill-sql (он держит длинные poll-транзакции — им нужен отдельный прямой пул или session-режим).

### 1.2 Read replicas + разделение чтения/записи
**Суть:** запись — в primary, чтение — с реплик. CQRS делает это бесплатным: read models уже отделены интерфейсами.
**Когда:** чтения >> записей (каталог аукционов листают в 1000× чаще, чем ставят).
**Ловушка:** replication lag — «сделал ставку, обновил страницу, ставки нет». Решения: read-your-writes (после записи юзер читает с primary, sticky на N секунд), либо UI-оптимизм.
**Molot:** `AuctionCardReadModel`/`ActiveCatalogReadModel` получают DSN реплики — меняется только composition root. Ставки и сага — всегда primary.

### 1.3 Партиционирование таблиц
**Суть:** время-ориентированные таблицы (ставки, события, ledger, аудит) режутся по диапазонам дат — индексы остаются маленькими, старые партиции отцепляются мгновенно (DROP вместо DELETE).
**Когда:** таблица >50-100M строк или ретеншн-политика «храним N месяцев горячими».
**Ловушка:** PK обязан включать ключ партиционирования; уникальность через партиции не работает.
**Molot:** `auction_bids`, watermill-таблицы, будущий ledger — кандидаты на range-партиции по месяцу.

### 1.4 Шардирование
**Суть:** данные режутся по ключу (auction_id, user_id) на независимые БД. Последний резерв — после реплик, партиций, кэша.
**Когда:** запись упёрлась в один primary физически (десятки тысяч TPS записи).
**Ловушка:** кросс-шардовые транзакции и JOIN-ы исчезают — сага и outbox должны жить внутри шарда; ресолвер шарда (consistent hashing) становится критичной инфраструктурой.
**Molot:** граница агрегата = граница транзакции (правило аудита) — шардирование по auction_id ложится без переписывания домена. Это и есть скрытая выгода DDD.

### 1.5 Hot row — наша главная специфика
**Суть:** все ставки одного горячего аукциона бьют в ОДНУ строку `auctions` (snapshot+version) — row lock сериализует, под снайпинг-финалом это очередь.
**Когда:** топовый лот, сотни ставок/сек.
**Решения по нарастанию:** (1) короткие транзакции (уже); (2) очередь-на-агрегат: ставки горячего лота идут через partitioned consumer (Kafka key=auction_id) — один воркер на лот, ноль конфликтов версий, батч-аппенд истории; (3) striped counters для счётчиков просмотров/интереса (не для денег!).
**Molot:** архитектурно готово — `PlaceBid` уже команда; перевод на async с client-generated BidID не меняет контракт (204 уже сейчас).

### 1.6 Горячее/холодное разделение
**Суть:** завершённые аукционы старше N месяцев — в архивную таблицу/S3 (parquet), основная БД держит рабочее множество.
**Ловушка:** «архив» без инструмента чтения = потерянные данные; нужен путь обратного доступа.

## 2. Кэширование

### 2.1 Cache-aside + защита от stampede
**Суть:** читаем кэш → промах → читаем БД → кладём с TTL. При истечении горячего ключа тысяча запросов ломится в БД одновременно (stampede).
**Мастхэв-защита:** `golang.org/x/sync/singleflight` — один полёт в БД на ключ, остальные ждут результат. Плюс jitter на TTL (не все ключи истекают разом) и stale-while-revalidate (отдаём протухшее, обновляем фоном).
**Molot:** каталог и карточка — идеальные кандидаты. Ставки/инвойсы/сага — НИКОГДА из кэша (деньги читаются из источника истины).

### 2.2 Двухуровневый кэш
**Суть:** L1 in-process (ristretto/otter, микросекунды, на инстанс) → L2 Redis (миллисекунды, общий) → БД.
**Ловушка:** L1 рассинхронизируется между инстансами — инвалидация только по TTL (короткий, секунды) либо по событию через pub/sub.
**Molot:** интеграционные события уже есть — `BidPlacedV1` инвалидирует ключ карточки. Event-driven инвалидация почти бесплатна.

### 2.3 CDN / edge
**Суть:** статика и анонимные GET-ы (каталог) — на CDN с `Cache-Control`/`ETag`/`stale-while-revalidate`.
**Ловушка:** случайно закэшировать персональное (заголовок `Vary`, приватные эндпоинты — `no-store`, у нас уже NoCache на /api).

## 3. Очереди и асинхронность

### 3.1 Backpressure — отказ лучше тихой деградации
**Суть:** каждая очередь bounded; полная очередь = быстрый отказ (429/503 + Retry-After), а не растущая латентность для всех.
**Ловушка:** unbounded каналы/буферы в Go — OOM в час пик. Любой `make(chan T)` без осмысленного размера в горячем пути — code smell.
**Molot:** HTTP уже синхронный (естественный backpressure через пул коннектов); при переходе ставок на очередь (1.5) — лимит глубины на топик + 429.

### 3.2 Partitioned consumers
**Суть:** Kafka-партиции по ключу агрегата: порядок гарантирован внутри ключа, параллелизм — между ключами.
**Ловушка:** перекошенный ключ (один мега-аукцион) = одна горячая партиция; следить за per-partition lag.
**Molot:** ADR-0002 уже запланировал Kafka; ключ = auction_id, хендлеры уже идемпотентны — переезд без переписывания логики.

### 3.3 Микробатчинг
**Суть:** N вставок одной транзакцией/COPY вместо N транзакций — на порядок дешевле для БД.
**Molot:** append истории ставок и проекции каталога при async-ставках; pgx `CopyFrom` для архивации.

### 3.4 Retry budget вместо наивных ретраев
**Суть:** ретраи с экспонентой + jitter И бюджетом (≤10% добавочного трафика) — иначе ретраи сами добивают деградирующую систему (retry storm).
**Ловушка:** ретраить можно только идемпотентное (у нас всё money-критичное уже идемпотентно — это предусловие, оно выполнено).

## 4. Защита от перегрузки (resilience)

### 4.1 Тотальные таймауты и дедлайны
**Суть:** у КАЖДОГО исходящего вызова таймаут; у запроса — сквозной дедлайн (context), который сужается вниз по стеку. Без дедлайна один зависший PSP съедает все горутины.
**Molot:** context уже сквозной; добавить явные `context.WithTimeout` бюджеты: HTTP-запрос 5s → PSP 3s → БД 1s.

### 4.2 Circuit breaker + bulkhead
**Суть:** breaker (gobreaker/sony) переводит падающую зависимость в fail-fast; bulkhead изолирует пулы (PSP-вызовы не съедают коннекты ставок).
**Ловушка:** breaker без fallback = просто быстрая ошибка; продумать деградацию (очередь отложенных оплат).
**Molot:** PSP — первый кандидат (уже есть `ErrPSPUnavailable` и идемпотентный протокол — breaker встаёт в InstrumentedPSP-декоратор одной строкой архитектурно).

### 4.3 Rate limiting по уровням
**Суть:** edge (nginx/envoy, по IP) → юзер (token bucket в Redis, по user_id) → эндпоинт (дорогие операции жёстче).
**Ловушка:** in-memory лимитер не работает на >1 инстансе; Redis-лимитер — единая точка (локальный fallback при недоступности).
**Molot:** `PlaceBid` per-user (анти-бот), `RegisterParticipant` per-IP (анти-спам); стыкуется с velocity-лимитами антифрода (ROADMAP 6.3.2).

### 4.4 Load shedding и приоритеты
**Суть:** при перегрузе сбрасываем дешёвое ради дорогого: каталог отдаём из протухшего кэша/503, ставки и оплаты обслуживаем всегда. Признак перегруза — глубина очереди/латентность, не CPU.
**Molot:** классификация готова в самой архитектуре: queries — sheddable, commands денежные — нет.

### 4.5 Graceful degradation
**Суть:** деградируют фичи, не система: отвалился notification — аукционы работают; отвалился PSP — ставки работают, оплаты копятся в отложенные.
**Molot:** контексты уже изолированы шиной — деградация по построению. Это вторая скрытая выгода event-driven.

## 5. Горизонтальное масштабирование

### 5.1 Stateless app
**Суть:** инстансы взаимозаменяемы: состояние в БД/кэше, сессии в JWT, файлы в S3. Тогда масштабирование = «добавь реплику за LB».
**Molot:** уже выполнено (JWT, state в PG) — можно запускать N инстансов хоть сейчас; гонки воркеров разруливают guard-ы агрегатов (проверено race-тестами).

### 5.2 Воркеры на N репликах: lease вместо «кто успел»
**Суть:** сейчас реплики Molot дерутся за `FOR UPDATE` (корректно, но в холостую). На большом масштабе — leader lease (advisory lock с TTL) либо `SELECT ... FOR UPDATE SKIP LOCKED` как распределение работы между репликами.
**Ловушка fencing:** любой распределённый лок без fencing token опасен — процесс, потерявший lease по GC-паузе, должен быть отвергнут хранилищем (у нас роль fencing уже играет `version` агрегата — паттерн выполнен неявно, задокументировать).

### 5.3 Идемпотентность — фундамент всего
**Суть:** at-least-once везде (ретраи, redelivery, дубли LB) ⇒ каждый обработчик идемпотентен. Без этого ни масштабирование, ни очереди, ни ретраи невозможны.
**Molot:** выполнено тотально (§6.6 ARCHITECTURE) — это главная причина, почему систему МОЖНО масштабировать.

## 6. Сеть и вход

- **L7 балансировка** (envoy/nginx): health-check ejection (наш /readyz уже готов), connection draining при деплое (graceful shutdown есть), keep-alive пулы.
- **gRPC между сервисами** при выносе контекста (фасад → gRPC-адаптер, ADR-0001 это предвидел); HTTP/2 мультиплексирование.
- **Multi-region** — только при реальном требовании: async-репликация + region-локальные чтения; для аукциона глобальный порядок ставок = одна primary-region запись (свет быстрее не станет — это физика, а не инженерия).

## 7. Наблюдаемость под нагрузкой

- **Гистограммы, не средние**: p50/p95/p99 (уже — duration histograms); среднее под нагрузкой лжёт.
- **USE для ресурсов** (utilization/saturation/errors: пул БД, глубина очередей — `molot_bus_oldest_message_age` уже есть) + **RED для сервисов** (есть).
- **Tail-based sampling** в otel-collector: 100% ошибочных и медленных трейсов, 1% остальных — иначе хайлоад утопит трейс-стор.
- **SLO + error budget** как контур управления: бюджет горит → фичи стоп, надёжность чинится (ROADMAP 1.1).

## 8. Go-специфика под нагрузкой

| Паттерн | Зачем |
|---|---|
| `GOMEMLIMIT` + мониторинг GC (`/debug/pprof`, runtime metrics — уже собираются) | контейнер без лимита = OOMKill в пик |
| `singleflight` | stampede-защита кэша и дорогих запросов |
| `errgroup.WithContext` + `SetLimit` | bounded параллелизм вместо безлимитных горутин |
| `sync.Pool` для горячих аллокаций (буферы сериализации) | давление на GC — главный убийца латентности Go |
| Прекомпилированные statements / `pgx` named cache | парсинг SQL на каждый запрос дорог |
| Избегать contention: sharded locks, atomic для счётчиков | один мьютекс на горячем пути = последовательная система |
| `http.Server` таймауты (Read/Write/Idle) — проверить выставлены | slowloris и подвисшие клиенты |

## Чек-лист «минимум для прода под нагрузкой»

1. ☑ Идемпотентность всех обработчиков (есть)
2. ☑ Stateless app + graceful shutdown (есть)
3. ☑ Гистограммы латентности + lag шины (есть)
4. ☐ Таймаут-бюджеты на каждый исходящий вызов
5. ☐ Circuit breaker + bulkhead на PSP
6. ☐ Rate limiting (edge + user)
7. ☐ singleflight-кэш каталога с event-инвалидацией
8. ☐ PgBouncer + read replica для query-стороны
9. ☐ Load shedding: queries деградируют, команды с деньгами — никогда
10. ☐ Tail-based sampling + SLO-алерты

Пункты 4-7 — следующий разумный шаг (S-M каждый); 8-10 — при реальном росте трафика.
