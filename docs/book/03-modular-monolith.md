# Глава 3. Модульный монолит: границы без сети

## Зачем читать

Вы начинаете новый сервис. Команда небольшая, домен ещё не устоялся, но все знают: «нужны микросервисы, иначе потом не распилишь». Через год оказывается, что каждая фича требует трогать четыре репозитория, деплоить синхронно и писать интеграционные тесты, которые падают чаще, чем проходят. Появилась сеть, появился тулинг, а порядка больше не стало.

Эта глава объясняет, почему так происходит, и показывает на реальном коде Molot, как держать строгие архитектурные границы внутри одного бинаря — без сети, но с теми же гарантиями изоляции, которые обычно приписывают микросервисам.

---

## Проблема: distributed monolith как худший исход

Микросервисы решают конкретную инженерную задачу: позволить разным командам деплоить независимо. Ключевое слово — **командам**, а не коду. Когда микросервисы вводят ради «порядка в коде» до того, как домен изучен и границы проверены временем, получается distributed monolith.

Distributed monolith — это система с той же внутренней связностью, что и обычный монолит, но с дополнительными накладными расходами:

- синхронные HTTP/gRPC-цепочки между сервисами: любой uptime ниже 100% бьёт по доступности всего флоу;
- распределённые транзакции: двухфазный коммит либо сага с нуля на каждой границе;
- версионирование API между сервисами: добавить поле в запрос — это теперь координация трёх команд;
- зоопарк инфраструктуры: отдельные базы, брокеры, service mesh, трассировка через десятки сервисов.

При этом главного бонуса — независимого деплоя — нет: если фича требует синхронного изменения трёх сервисов, их всё равно катят вместе.

Правильные границы в начале проекта выбрать почти невозможно — домен ещё не изучен. ADR-0001 Molot прямо фиксирует этот факт: «высокий риск distributed monolith при ещё не проверенных границах».

---

## Теория: что такое модульный монолит

**Монолит** — один процесс, один деплой. Граней нет вообще: любой код может вызвать любой другой.

**Микросервисы** — N процессов, N деплоев. Граница — сеть. Всё, что пересекает границу, сериализуется, теряет транзакционность, требует retry-логики.

**Модульный монолит** — один процесс, один деплой, но с явными границами внутри. Граница — не сеть, а соглашение, которое machine-checked: компилятор и CI не дают нарушить её.

Ключевое утверждение: **граница и сеть — независимые концепции**. Граница означает «этот код не знает о деталях того кода». Сеть — лишь один из механизмов её enforcement, и далеко не самый дешёвый.

### Три свойства настоящей границы

1. **Не нарушается случайно.** Граница, которую нарушают из-за спешки или незнания, — не граница. Нужен механизм, который не зависит от дисциплины.

2. **Единственный публичный контракт.** Всё, что снаружи — события и явный фасад. Детали внутри — приватны.

3. **Автономная схема данных.** Общая БД у нескольких «сервисов» — это не граница; это общий глобальный state с иллюзией изоляции.

## Как в Molot

### Структура модуля: шесть поддиректорий

Каждый bounded context живёт в `internal/<ctx>/` и имеет строго определённую структуру:

```
internal/auction/
├── domain/        # stdlib-only; бизнес-правила, агрегаты, VO, sentinel-ошибки
├── app/           # use cases: команды и запросы; consumer-side интерфейсы
│   ├── command/
│   └── query/
├── ports/         # входящий мир: HTTP, воркеры, подписки на события
├── adapters/      # исходящий мир: Postgres, in-memory, PSP, event mapper
├── events/        # ЕДИНСТВЕННЫЙ пакет, импортируемый другими контекстами
└── service/       # Facade + NewService: точка сборки контекста
```

То же самое — у `billing`, `participant`, `settlement`. Исключение по документу: `notification` не имеет `domain/app`-слоёв (тривиальный event → template → send), и это явно задокументировано в пакете с условием пересмотра.

Пять контекстов получены из event-storming потока «лот → ставки → молоток → счёт → оплата/компенсация»: каждый излом потока, где меняется ответственность и язык, — граница.

### Enforcement границ: depguard в CI

Граница enforcement-ится компилятором (пакеты внутри `internal/` недоступны снаружи модуля) и `depguard` в CI. Вот реальный конфиг из `.golangci.yml`:

```yaml
linters-settings:
  depguard:
    rules:
      domain-imports-nothing-above:
        list-mode: lax
        files:
          - "**/internal/**/domain/**"
        deny:
          - pkg: molot/internal/auction/app
            desc: domain must not import app
          - pkg: molot/internal/auction/ports
            desc: domain must not import ports
          - pkg: molot/internal/auction/adapters
            desc: domain must not import adapters
          # ... аналогично для каждого контекста

      app-imports-domain-only:
        list-mode: lax
        files:
          - "**/internal/**/app/**"
        deny:
          - pkg: molot/internal/auction/ports
            desc: app must not import ports
          - pkg: molot/internal/auction/adapters
            desc: app must not import adapters
          # ...

      ports-never-import-adapters:
        list-mode: lax
        files:
          - "**/internal/**/ports/**"
        deny:
          - pkg: molot/internal/auction/adapters
            desc: ports must not import adapters
          # ...

      common-is-business-free:
        list-mode: lax
        files:
          - "**/internal/common/**"
        deny:
          - pkg: molot/internal/auction
            desc: internal/common must not import a bounded context
          # ... аналогично для каждого контекста
```

PR, нарушающий любое из этих правил, не проходит CI. Это не code review, не договорённость — это автоматическая проверка. Инженер физически не может случайно импортировать чужой domain.

Дополнительный инструмент — `go-cleanarch`: проверяет направление стрелок `domain → app → ports/adapters`. Оба линтера работают в одном `make lint`.

### Схема-на-контекст в БД

Вторая линия enforcement — Postgres-схемы. Каждый контекст владеет своей схемой:

- `auction.auctions`, `auction.auction_bids`, `auction.bidder_profiles`, `auction.catalog_items`
- `billing.invoices`
- `settlement.settlements`
- `participant.participants`
- `notification.sent_notifications`, `notification.recipients`

Cross-schema запросы (например, `SELECT * FROM billing.invoices JOIN auction.auctions ...`) — fail на code review. У `billing` нет SELECT-прав на `auction.*`. Это не техническая блокировка Postgres GRANT, это правило ревью, зафиксированное в ADR-0001: «импорт чужого `domain/` и запросы к чужим Postgres-схемам — fail CI/ревью».

Миграции — per-context, embedded в бинарь:

```go
// internal/monolith/app.go:169-176
migrations := []contextMigrations{
    {table: "goose_db_version_participant", fs: participantservice.Migrations},
    {table: "goose_db_version_auction",     fs: auctionservice.Migrations},
    {table: "goose_db_version_billing",     fs: billingservice.Migrations()},
    {table: "goose_db_version_settlement",  fs: settlementservice.Migrations},
    {table: "goose_db_version_notification", fs: notificationservice.Migrations},
}
```

Каждый контекст хранит свои `*.sql` в `adapters/migrations/` и знает только свою схему.

### События — единственный публичный канал

Контексты общаются двумя способами:

**Асинхронно** — через интеграционные события из `internal/<ctx>/events/`. Это единственный пакет, который другой контекст может импортировать. Events плоские, версионированные (`AuctionClosedV1`), только примитивы + `time.Time`, схема append-only.

Пример контракта события (ARCHITECTURE.md §4.2):

```go
// internal/auction/events/events.go
type AuctionClosedV1 struct {
    EventID   string `json:"event_id"`
    AuctionID string `json:"auction_id"`
    SellerID  string `json:"seller_id"`
    Outcome   string `json:"outcome"` // sold|not_sold

    WinnerID          string  `json:"winner_id"`
    HammerPriceMinor  int64   `json:"hammer_price_minor"`
    Currency          string  `json:"currency"`

    RunnerUpBidderID  string  `json:"runner_up_bidder_id"`
    RunnerUpAmountMinor int64 `json:"runner_up_amount_minor"`
    RunnerUpQualifies bool    `json:"runner_up_qualifies"` // ← резервная цена скрыта, только готовый bool

    RelistGeneration int       `json:"relist_generation"`
    OccurredAt       time.Time `json:"occurred_at"`
}
```

Обратите внимание: резервная цена аукциона (`reserve`) — внутренний инвариант `auction`-домена, она никогда не покидает контекст. Settlement получает только `RunnerUpQualifies bool` — готовое решение, вычисленное auction. Это и есть граница в действии: settlement не знает о reserve, auction не знает о settlement.

**Синхронно** — только для фасадных команд саги (settlement зовёт auction и billing). Синхронный вызов оформляется через consumer-defined интерфейс: settlement объявляет у себя `auctionGateway` с нужными методами, а адаптер реализует его, вызывая фасад auction.

```go
// settlement/app/handlers.go — consumer-side интерфейс объявляет потребитель
type auctionGateway interface {
    AwardToRunnerUp(ctx context.Context, auctionID ...) error
    RelistAuction(ctx context.Context, ...) error
    MarkSaleFailed(ctx context.Context, ...) error
    ConfirmSettlement(ctx context.Context, ...) error
}
```

Auction ничего не знает о settlement. Settlement знает только о форме интерфейса, который сам же объявил. Это паттерн `io.Writer` в масштабе архитектуры.

Прямой импорт чужого `domain/` запрещён: `Money` осознанно продублирован в `auction` и `billing` — потому что у них разные причины меняться.

### Composition root: сборка в одном месте

Весь граф зависимостей собирается в `internal/monolith/app.go`. Это единственное место, где конкретные типы встречаются друг с другом:

```go
// internal/monolith/app.go:205-268

auctionSvc, err := auctionservice.NewService(auctionservice.Deps{
    DB: db, Logger: logger,
    PlatformCurrency:   cfg.PlatformCurrency,
    VerifyAboveMinor:   cfg.VerifyAboveMinor,
    SnipeWindow:        cfg.SnipeWindow,
    ClosingPollInterval: cfg.ClosingPollInterval,
    // ...
})
if err != nil {
    return nil, fmt.Errorf("assemble auction context: %w", err)
}
auctionSvc.RegisterHTTP(apiRouter)
if err := auctionSvc.RegisterEventHandlers(wmRouter, subscriberConstructor); err != nil {
    return nil, fmt.Errorf("register auction event handlers: %w", err)
}

// ...

settlementSvc, err := settlementservice.NewService(settlementservice.Deps{
    DB:            db,
    AuctionFacade: auctionSvc.Facade(),   // <-- единственное место, где settlement видит auction конкретно
    BillingFacade: billingSvc.Facade(),
    // ...
})
```

Тот же `newApplication` вызывают и prod-точка входа (`NewApplication`), и компонентные тесты (`NewComponentTestApplication`). Разница только в адаптерах: prod получает настоящие OTel-провайдеры, тесты — noop. DI-фреймворк не нужен: файл помещается в 330 строк и читается линейно.

Конструкторы паникуют на nil-зависимость. Если сборка некорректна — процесс падает при старте, а не в три часа ночи на первом запросе.

## Трейдоффы и альтернативы

Модульный монолит — не серебряная пуля. Честный список того, что вы теряете:

**Нет независимого деплоя.** Все контексты катятся вместе. Если billing нужен hotfix, весь монолит проходит deployment pipeline. Это цена одного бинаря.

**Нет независимого масштабирования.** Реплика — это всегда весь бинарь. Если `settlement` обрабатывает тяжёлые саги, а `participant` почти пустой — обе компоненты получат одинаковое число реплик. В Molot это решается дизайном воркеров: они конкурентны, row-lock на агрегате корректно разрешает гонки. Но горизонтальный масштаб только одного контекста — невозможен без выноса.

**Соблазн срезать границу.** В одном процессе технически ничто не мешает добавить импорт. Только CI. Это работает пока команда культуру поддерживает и линтеры не отключены.

**Альтернатива: слоистый монолит без контекстов** — отклонена в ADR-0001: «связность растёт неконтролируемо, выноса нет, границы пришлось бы вводить задним числом». Это стартовая точка большинства legacy-систем.

**Альтернатива: микросервисы с первого дня** — также отклонена: «операционная цена без организационной нужды, высокий риск distributed monolith при ещё не проверенных границах».

**Правильный выбор** зависит от размера команды и стадии проекта. Molot — один разработчик, MVP-масштаб, домен изучается в процессе. Модульный монолит — оптимум. Когда команды становятся независимыми, а release-циклы расходятся, контексты выносятся дёшево — именно потому, что граница была реальной с самого начала.

## Сравнительная таблица

| Ось | Монолит (слоистый) | Модульный монолит | Микросервисы |
|---|---|---|---|
| **Транзакции** | Тривиальны, один контекст БД | Один Postgres, схемы изолированы; transactional outbox для событий | Распределённые; сага или 2PC |
| **Деплой** | Один бинарь, простой | Один бинарь, простой | N деплоев; координация версий |
| **Отладка** | Один процесс, простой stack trace | Один процесс; сквозной трейс через контексты одним span-деревом | Трейсинг обязателен; ошибки теряются между сервисами |
| **Команда** | Не масштабируется: все трогают всё | Масштабируется на 2–3 команды через зоны владения контекстами | Оптимально для 3+ независимых команд с разными release-циклами |
| **Стоимость границы** | Нет границ → нет изоляции | Низкая: CI-правило + схема Postgres | Высокая: сеть, версионирование, retries, distributed tracing |
| **Независимый деплой** | Нет | Нет (один бинарь) | Да |
| **Независимое масштабирование** | Нет | Нет (реплика — весь бинарь) | Да |

Вывод из таблицы: модульный монолит даёт изоляцию и масштаб команд почти бесплатно, но не даёт независимого деплоя и масштабирования отдельного контекста. Это сознательный трейдофф, зафиксированный в ADR-0001:

> «(−) Масштабирование — только репликами целого бинаря; воркеры и event-хендлеры спроектированы под конкурентные реплики (row lock + guard-ы агрегатов).»

## Критерии выноса контекста в отдельный процесс

Выносить контекст стоит, когда выполняется хотя бы одно из условий как **измеримый факт**, а не предположение:

1. **Масштаб команды**: контекст стабильно развивает отдельная команда, которой мешают общие деплой-циклы.
2. **Масштаб нагрузки**: profiling показывает, что конкретный контекст — узкое место, и горизонтальное масштабирование только его решит задачу дешевле, чем масштабировать весь монолит.
3. **Изоляция отказа**: требование SLA на контекст принципиально отличается от остальных, и отказ одного не должен влиять на другие.
4. **Разные технологические стеки**: контекст обоснованно требует другого языка, рантайма или инфраструктуры.

Мода, «так принято», «на будущее» — не критерии.

### Selective deployment как полпути: ROADMAP 7.2.3

ROADMAP Molot описывает промежуточный шаг перед полноценным выносом:

> «Selective deployment — два бинаря из тех же модулей: `cmd/monolith` без notification + отдельный `cmd/notifier` только с ним (другая комбинация composition root; шина у них общая — watermill-sql/Kafka). Доказывает, что контексты реально независимы — модуль выносится в отдельный процесс пересборкой composition root, без правки домена/app/контрактов.»

Это означает: если границы держатся как следует, вынести контекст — это изменить composition root и подключить gRPC-адаптер вместо in-process фасада. Домен, app-логика и контракты событий не трогаются.

Вынос заложен дизайном, а не кодом «на будущее». ADR-0001:

> «Путь выноса заложен дизайном, не кодом «на будущее»: контекст → сервис = замена facade-адаптера на gRPC и watermill-sql на Kafka (ADR-0002); контракты `events/` и хендлеры не меняются.»

## Типичные ошибки

### 1. Нарезка по существительным

`UserService`, `OrderService`, `ProductService` — это не bounded contexts, это технические группировки сущностей. Граница контекста определяется причиной изменения, а не названием сущности.

Литмус-тест из ARCHITECTURE.md: «изменить шаг ставки» затрагивает только `auction`; «изменить формулу комиссии» — только `billing`; «новая ветка компенсации» — только `settlement». Если новая фича не помещается в один модуль — чинится граница, а не фича.

### 2. «Микросервисы» с общей БД

Это distributed monolith в худшем варианте. Если два сервиса читают одну таблицу, граница — иллюзия. Любое изменение схемы требует координации обоих. При этом все накладные расходы сети присутствуют, а транзакционности нет.

### 3. Sync-цепочки вместо событий

Если `auction` при закрытии напрямую зовёт `billing.IssueInvoice` синхронно — это скрытая сцепка. Через год граф вызовов станет спагетти. В Molot обратная схема: `auction` публикует `AuctionClosedV1`, `settlement` подписывается и сам инициирует `IssueInvoice` через свой фасад. Auction не знает, кто слушает.

### 4. Нарушение границы через «общий» пакет

`internal/common` — сильный соблазн: «положим сюда Money, и все будут использовать». В Molot это явно запрещено. `Money` продублирован в `auction` и `billing` осознанно: у каждого контекста своя валидация, свой инвариант, своя причина меняться. `internal/common` содержит только инфраструктуру (auth, tracing, logging, watermill-обёртки), ноль бизнес-типов.

```yaml
# .golangci.yml
common-is-business-free:
  files:
    - "**/internal/common/**"
  deny:
    - pkg: molot/internal/auction
      desc: internal/common must not import a bounded context
    - pkg: molot/internal/billing
      desc: internal/common must not import a bounded context
    # ...
```

### 5. «Соблазн срезать границу»

ADR-0001 прямо называет это:

> «(−) Соблазн «срезать» границу внутри одного процесса постоянен — поэтому guard-ы в CI, а решения, тянущие чужой домен (правила second-chance), перенесены в данные событий (`RunnerUpQualifies`) и домен саги.»

Конкретный пример: сага settlement должна знать, квалифицировался ли runner-up по резервной цене. Резервная цена — данные auction-домена. Решение: auction при закрытии вычисляет `RunnerUpQualifies bool` и публикует готовый результат в `AuctionClosedV1`. Settlement получает ответ, не зная о существовании резервной цены. Граница держится.

## Чек-лист

Перед тем как добавлять новый контекст или проверять существующий:

- [ ] Граница получена из domain event-storming, а не из технической группировки или названия сущности
- [ ] Литмус-тест проходит: типичная фича меняет один контекст
- [ ] Структура `domain/app/ports/adapters/events/service` соблюдается
- [ ] CI проверяет направление импортов (`depguard` + `go-cleanarch`)
- [ ] Контекст владеет отдельной Postgres-схемой; cross-schema JOIN отсутствует
- [ ] Единственный публичный пакет — `events/`; синхронный фасад — через consumer-defined интерфейс
- [ ] Интеграционные события плоские, версионированные (`V1`), только примитивы
- [ ] Бизнес-тип не попал в `internal/common`
- [ ] Решение о выносе контекста принято по измеримому факту, а не по предположению
