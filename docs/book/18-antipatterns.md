# Глава 18. Каталог антипаттернов

## Зачем читать

Хороший дизайн легче объяснять от обратного: не «делай вот так», а «видишь вот это в коде — остановись». Эта глава — каталог ошибок, которые появляются не от незнания Go, а от незнания того, чем кончаются привычные shortcuts через полгода в production. У всех у них одно неприятное свойство: в момент написания они выглядели разумно. Никто не пишет анемичную модель из вредности — её пишут, потому что «так быстрее», и первые месяцы это даже правда.

Каждый раздел устроен одинаково: название антипаттерна, как он выглядит в коде (помечено **— антипример**), чем это заканчивается конкретно — самая важная часть, читайте её внимательнее кода — и как сделано в Molot с указанием файла. В конце — сводная таблица «запах → глава».

Антипаттерны сгруппированы по природе боли: сначала доменные (где ломается модель), затем инфраструктурные (где ломается граница слоёв), затем архитектурные (где ломается система в целом), затем тестовые и процессные. Узнаете свой код — это нормально.

## Группа 1. «Java в Golang»

**Как выглядит.** В команду приходит сильный разработчик с десятью годами Java или C# — и Go-проект обрастает знакомыми силуэтами: каждый «сервис» — struct с одним методом на use case, stateless «domain service object» вместо простой функции, интерфейс на единственную реализацию «ради расширяемости», `CalculatePriceService.Calculate(...)` вместо `func CalculatePrice(a Auction) Money`.

```go
// — антипример
type BidValidatorService struct{}

func (s BidValidatorService) Validate(a *Auction, amount Money) error {
    // логика, которая — просто функция
}
```

На что смотреть: у `BidValidatorService` нет полей. Этот struct существует только чтобы у функции был receiver — то есть не существует ни для чего.

**Чем кончается через полгода.** В кодовой базе заводится слой «сервисов» без состояния, которые тем не менее надо мокировать. Интерфейсы разрастаются до десятков методов, тесты проверяют моки, а не логику. «Расширяемость» так и не пригодилась — вторая реализация не появилась никогда, а сложность осталась, как строительные леса вокруг давно сданного дома.

**Как правильно.** Stateless-вычисления — простые функции в доменном пакете. В Molot: `MinimalNextBid` и `CanSellerManageAuction` — пакетные функции без receiver-а, вызываются прямо из behavior-метода агрегата.

```go
// internal/auction/domain/auction/auction.go

// MinimalNextBid — пакетная функция, не «сервис»
func MinimalNextBid(a Auction) Money {
    if a.leadingBid.IsZero() {
        return a.startPrice
    }
    minNext, err := a.leadingBid.Amount().Add(a.increment)
    if err != nil {
        panic("auction: leading bid and increment currency diverged: " + err.Error())
    }
    return minNext
}

func CanSellerManageAuction(s SellerID, a Auction) error {
    if s != a.seller {
        return ForbiddenAuctionManagementError{Actor: s, Owner: a.seller}
    }
    return nil
}
```

На что смотреть: функцию можно вызвать, прочитать и протестировать без единого мока. Когда нужно разделить расчёт и мутацию — это два отдельных вызова, не один «сервис»; receiver появляется только при переходе состояния. (Глава 4.)

## Группа 2. Anemic model

**Как выглядит.** На первый взгляд всё невинно: доменные типы — «чистые данные» с публичными полями или тривиальными геттерами/сеттерами, бизнес-правила — в хендлерах. Состояние кодируется булевыми парами и указателями (`*string` как «опциональное»), роли — magic strings.

```go
// — антипример
type Auction struct {
    Status    string
    LeaderID  *string   // nil = нет ставок
    IsClosed  bool
    IsCancelled bool
}

// в хендлере:
if a.Status == "listed" && !a.IsClosed && a.LeaderID == nil {
    a.Status = "cancelled"
    a.IsCancelled = true
}
```

На что смотреть: на фрагмент в хендлере. Правило «отменить можно только активный аукцион без ставок» существует здесь в виде if-а — в одном из хендлеров. Главный вопрос: в скольких ещё?

**Чем кончается через полгода.** Правило продублировано в каждом хендлере, которому может понадобиться отмена: один проверил все условия, другой — половину, третий писался в пятницу. Невалидное состояние (`IsClosed=true` при `Status="listed"`) уходит в базу; через месяц его находит не тест, а аналитик — вопросом «почему у нас девяносто закрытых аукционов со статусом listed?». Тесты бессильны: нельзя сломать то, что не существует в одном месте.

**Как правильно.** Все поля приватные. Создание — только через валидирующий конструктор. Переходы — только через behavior-методы, где guard и изменение атомарны. Перечислимые состояния — отдельные value-object типы, не строки.

```go
// internal/auction/domain/auction/status.go

type Status struct{ s string }

var (
    StatusListed    = Status{"listed"}
    StatusCancelled = Status{"cancelled"}
    StatusClosed    = Status{"closed"}
)

func NewStatusFromString(s string) (Status, error) { ... }
func (s Status) IsZero() bool   { return s == Status{} }

// internal/auction/domain/auction/auction.go — Cancel атомарно проверяет и меняет
func (a *Auction) Cancel(by SellerID, now time.Time) error {
    if err := CanSellerManageAuction(by, *a); err != nil {
        return err
    }
    // ...
    if a.HasBids() {
        return ErrAuctionHasBids
    }
    a.status = StatusCancelled
    a.record(AuctionCancelled{OccurredAt: now})
    return nil
}
```

На что смотреть: `Cancel` нельзя выполнить «наполовину» — проверка прав, guard на ставки и смена статуса происходят либо вместе, либо никак. Снаружи агрегата нет способа получить `StatusCancelled` в обход проверок. (Глава 4.)

**Совет из практики.** Быстрый тест на анемию — grep по строковому литералу статуса: `rg '"listed"'`. Каждое вхождение вне доменного пакета — бизнес-правило, живущее своей жизнью; больше одного — рассинхрон уже есть, вы о нём просто ещё не знаете.

## Группа 3. Eight-thousanders — god-хендлеры

**Как выглядит.** Эндпоинт, начинавшийся как скромный «обновить аукцион», за год вырастает в `UpdateAuction(status *string, isClosed *bool, leaderID *string)` — функцию, которая делает разные вещи в зависимости от того, какие поля не nil. Внутри — стена if-ов вместо named behavior; пятьсот строк, и каждая когда-то была чьим-то срочным багфиксом.

```go
// — антипример
func (h *AuctionHandler) Update(w http.ResponseWriter, r *http.Request) {
    // разбираем все возможные поля
    // if req.Status == "cancelled" { ... }
    // if req.Status == "closed" && req.WinnerID != nil { ... }
    // if req.IsFailed { ... }
    // 400 строк ...
}
```

На что смотреть: у этого кода нет имени. «Update» — не поведение, а признание, что поведений много и все свалены в кучу.

**Чем кончается через полгода.** Добавить новое бизнес-правило — значит вписать if в середину и надеяться, что не задеты соседние ветки; надежда — плохая стратегия регрессии. Тестировать можно только через HTTP, поэтому corner cases не покрыты: ради каждого теста нужно поднимать весь сервер. Через полгода на вопрос «какие комбинации входов допустимы?» не ответит никто — включая автора. Особенно автора.

**Как правильно.** Один use case — одна named команда с `Handle(ctx, cmd) error`. Каждое поведение имеет имя в языке бизнеса. В Molot: `PlaceBid`, `CancelAuction`, `CloseAuction`, `AwardToRunnerUp`, `FailSale` — пять отдельных хендлеров, каждый в своём файле, каждый тестируется изолированно.

```go
// internal/auction/app/command/place_bid.go
type PlaceBid struct {
    AuctionID auction.AuctionID
    BidID     auction.BidID
    Bidder    auction.BidderID
    Amount    auction.Money
}

func (h PlaceBidHandler) Handle(ctx context.Context, cmd PlaceBid) error {
    bidder, err := h.profiles.BidderByID(ctx, cmd.Bidder)
    if err != nil {
        return err
    }
    return h.repo.Update(ctx, cmd.AuctionID, auction.ActorFromBidder(cmd.Bidder),
        func(ctx context.Context, a *auction.Auction) (*auction.Auction, error) {
            if _, err := a.PlaceBid(cmd.BidID, bidder, cmd.Amount, h.clock.Now()); err != nil {
                return nil, err
            }
            return a, nil
        })
}
```

На что смотреть: хендлер умещается на экран, и в нём нет ни одного бизнес-if-а — только оркестрация. Всё, что может пойти не так по бизнесу, живёт внутри `a.PlaceBid`. (Глава 7.)

## Группа 4. DB-теги на домене / один struct на всё

**Как выглядит.** Доменный тип несёт `db:`, `json:`, `bson:`-теги — одна структура работает и хранилищем, и API-ответом, и доменным объектом. Зачем три типа, когда поля совпадают? А когда совпадать перестают, появляется «починка» — обнуление поля перед сериализацией (`user.LastIP = nil`).

```go
// — антипример
type Auction struct {
    ID       string    `db:"id"   json:"id"`
    Status   string    `db:"status" json:"status"`
    LeaderID *string   `db:"leader_id" json:"leader_id,omitempty"`
    // ... и это же отдаётся в API, и это же читается из БД
}
```

На что смотреть: каждый тег — обещание другому слою; два набора тегов — обещания всем сразу, которые нельзя сдержать, не нарушив друг друга.

**Чем кончается через полгода.** Реальный инцидент из первоисточника: один struct на DB и API привёл к утечке поля `LastIP` всем пользователям — разработчик добавил поле в БД, не подумав, что оно автоматически появится в JSON-ответе. Заметьте: он не сделал ничего «опасного», просто добавил колонку — остальное сделала архитектура. После такого добавить поле в хранилище, не засветив его в API, можно только «заплатками».

**Как правильно.** Три отдельные модели: storage struct (с `db:`-тегами, в адаптере), domain type (без тегов, в `domain/`), transport DTO (для API, в `ports/`). Маппинг явный, в адаптере. В Molot:

```go
// internal/auction/adapters/auction_pg_repository.go

// pgAuction — storage model, живёт только в adapters/
type pgAuction struct {
    ID              uuid.UUID
    Status          string
    LeadingBidID    uuid.NullUUID
    LeadingAmountMinor sql.NullInt64
    Version         int64
    // ... db-поля
}

// доменный тип auction.Auction — без единого тега, в domain/
// transport DTO — отдельно, в ports/
```

На что смотреть: `pgAuction` живёт только в `adapters/` и меняется вслед за схемой БД, не дёргая ни домен, ни API. Цена — скучный явный маппинг; она заметно ниже, чем инцидент с утечкой. (Глава 3, глава 5.)

## Группа 5. DRY на данных

**Как выглядит.** «Зачем два struct, если поля одинаковые?» — возможно, самый дорогой вопрос в истории код-ревью. После него общий тип начинает обслуживать хранение, API и бизнес-логику одновременно.

```go
// — антипример
// один Bid используется везде: и в базе, и в API, и в домене
type Bid struct {
    ID        string  `db:"id" json:"id"`
    Amount    float64 `db:"amount" json:"amount"` // float64 для денег — отдельная боль
    BidderID  string  `db:"bidder_id" json:"bidder_id"`
}
```

На что смотреть: помимо двойных тегов — `float64` для денег (отдельная боль). Тип навязал всем трём слоям одно неподходящее представление.

**Чем кончается через полгода.** Потребители меняются по разным причинам: API — под требования клиента, БД — под оптимизацию запросов, домен — под бизнес-правила. Общий тип означает, что любое из трёх изменений дёргает остальные два. Поле добавили в таблицу — оно всплыло в API; убрали из API — сломался маппинг из БД. Появляются «адаптеры-заплатки» (`omitempty`, `json:"-"`), маскирующие проблему.

**Как правильно.** DRY — про знание и поведение, не про структуры данных: совпадение полей — это совпадение, а не общность. Три слоя — три модели, маппинг явный; небольшое дублирование — осознанный трейдофф ради независимости слоёв.

```go
// domain: Money — value object с инвариантами
// adapters: хранит int64 minor units в pgAuction
// ports: отдаёт в JSON как { "amount": 10050, "currency": "RUB" }
// — три разных представления одного факта
```

На что смотреть: каждое из трёх представлений отвечает своему слою — домену инварианты, базе точность, API стабильный контракт. (Глава 3.)

## Группа 6. Транзакции через context / неправильный updateFn

**Как выглядит.** Транзакция открывается в сервисе и кладётся в `context.Context` — «чтобы не таскать через параметры». Или наоборот: `*sql.Tx` честно прокидывается через пять слоёв. Или `updateFn` мутирует переданный агрегат и возвращает тот же указатель. Или — самый тихий вариант — забыт `SELECT ... FOR UPDATE`.

```go
// — антипример
func (s *AuctionService) PlaceBid(ctx context.Context, id string, amount int) error {
    tx, _ := s.db.BeginTx(ctx, nil)
    ctx = context.WithValue(ctx, "tx", tx) // магия через контекст
    a, _ := s.repo.Get(ctx, id)            // репо тихо достаёт tx
    a.Status = "bidded"                    // прямая мутация
    s.repo.Save(ctx, a)
    tx.Commit()
    return nil
}
```

На что смотреть: строка с `context.WithValue`. Транзакция стала невидимкой — её нет ни в одной сигнатуре, и какой код выполняется внутри неё, выясняется только чтением реализаций.

**Чем кончается через полгода.** Невидимое не проверяется: добавить код-путь, который не участвует в транзакции, тривиально — и незаметно, до первого расхождения данных. Без `FOR UPDATE` два одновременных запроса читают одно значение, и оба «выигрывают» ставку — молча, без единой ошибки в логах. А мутация переданного указателя оставляет адаптер в неведении, что именно персистировать.

**Как правильно.** Транзакция — деталь адаптера. `updateFn` возвращает новое значение. `FOR UPDATE` — в реализации `Update`. В Molot:

```go
// internal/common/postgres/postgres.go

func RunInTx(ctx context.Context, db *sql.DB,
    fn func(ctx context.Context, tx *sql.Tx) error) (err error) {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil {
        return fmt.Errorf("begin tx: %w", err)
    }
    defer func() { err = FinishTransaction(err, tx) }()
    return fn(ctx, tx)
}

// FinishTransaction комбинирует rollback-ошибку с исходной — ни одна не теряется
func FinishTransaction(err error, tx *sql.Tx) error {
    if err != nil {
        if rollbackErr := tx.Rollback(); rollbackErr != nil {
            return multierr.Combine(err, fmt.Errorf("rollback tx: %w", rollbackErr))
        }
        return err
    }
    if commitErr := tx.Commit(); commitErr != nil {
        return fmt.Errorf("commit tx: %w", commitErr)
    }
    return nil
}
```

На что смотреть: `FinishTransaction` не теряет ни одну из двух ошибок — аккуратность, которая окупается в три часа ночи, когда по логу нужно понять, что упало первым.

```go
// internal/auction/adapters/auction_pg_repository.go — SELECT ... FOR UPDATE
row := tx.QueryRowContext(ctx,
    `SELECT `+auctionColumns+` FROM auction.auctions WHERE id = $1 FOR UPDATE`, id.UUID())
```

А `FOR UPDATE` живёт в адаптере — один раз, для всех use cases сразу. Хендлеры не могут его «забыть», потому что не знают о нём. (Глава 5.)

**Где вы на это наступите.** Гонка без `FOR UPDATE` не ловится локально: in-memory репозиторий, один пользователь. В production хватает двух вкладок — два клика по «Сделать ставку» в одну секунду, и обе прошли. Если read-modify-write не защищён блокировкой или версией, баг уже в проде — счёт просто ещё не выставлен.

## Группа 7. Per-use-case методы на репозитории

**Как выглядит.** Репозиторий начинает разбираться в бизнесе: `ApproveRescheduleTraining(ctx, id, userID)`, `CancelAuctionIfNoBids(ctx, id)`. Валидация переезжает в тело метода — «там же удобно, данные рядом». `sql.ErrNoRows` возвращается как ошибка в GetOrCreate-сценарии.

```go
// — антипример
type AuctionRepository interface {
    GetOpenAuctionsForSeller(ctx context.Context, sellerID string) ([]Auction, error)
    CancelIfNoBids(ctx context.Context, id string) error
    PlaceBidAndNotify(ctx context.Context, id, bidderID string, amount int) error
}
```

На что смотреть: `PlaceBidAndNotify` на интерфейсе хранилища. Репозиторий, умеющий ещё и «уведомить», — уже не репозиторий, а второй app-слой с прямым доступом к SQL.

**Чем кончается через полгода.** Бизнес-правила расселяются на два этажа — часть в use case-ах, часть в репозитории, — и при каждом изменении нужно помнить про оба. Интерфейс растёт вместе со списком use cases, in-memory реализация хронически отстаёт, и однажды её перестают чинить. С этого момента быстрых тестов у вас нет.

**Как правильно.** Репозиторий глуп: `Add / Get / Update`. Вся логика — в доменном агрегате внутри `updateFn`. In-memory реализация — полный заменитель Postgres.

```go
// internal/auction/domain/auction/repository.go

type Repository interface {
    Add(ctx context.Context, a *Auction) error
    Get(ctx context.Context, id AuctionID) (*Auction, error)
    Update(ctx context.Context, id AuctionID, actor Actor,
        updateFn func(ctx context.Context, a *Auction) (*Auction, error)) error
    UpdateAsSystem(ctx context.Context, id AuctionID,
        updateFn func(ctx context.Context, a *Auction) (*Auction, error)) error
}
```

На что смотреть: этот интерфейс не изменится от появления двадцатого use case — всем хватит `Update` со своим `updateFn`. Глупость репозитория — это его стабильность. (Глава 5.)

## Группа 8. Guard-if авторизация по хендлерам

**Как выглядит.** В каждом хендлере — ручной `if user.Role != "admin" { return 403 }`. Авторизация существует как дисциплина («мы всегда проверяем!»), а не как свойство системы. Системные фоновые потоки ходят под fake user с нужными правами. Identity достаётся из `context.Value(...)` — иногда прямо внутри репозитория.

```go
// — антипример
func (h *Handler) CancelAuction(w http.ResponseWriter, r *http.Request) {
    user := r.Context().Value("user").(User)
    auction, _ := h.repo.Get(r.Context(), id)
    if auction.SellerID != user.ID { // забыл здесь → privilege escalation
        http.Error(w, "forbidden", 403)
        return
    }
    // ...
}
```

На что смотреть: комментарий в антипримере честнее любого аудита — «забыл здесь → privilege escalation». Вся защита держится на том, что каждый будущий автор каждого хендлера про этот if вспомнит.

**Чем кончается через полгода.** Harbor CVE: разработчик добавил новый endpoint и забыл проверить права — эскалация привилегий. «Забыть проверить» — не человеческая ошибка, а системная проблема дизайна, где правило хранится в головах, а не в компиляторе. Люди забывают — это их документированное свойство; дизайн, рассчитывающий на обратное, сломан до первого инцидента.

**Как правильно.** Действующий пользователь — явный типизированный параметр. Авторизационное правило — чистая доменная функция. Вызов правила — внутри адаптера, мимо которого нет код-пути.

```go
// internal/auction/domain/auction/repository.go
Update(ctx context.Context, id AuctionID, actor Actor,
    updateFn func(ctx context.Context, a *Auction) (*Auction, error)) error

// actor — обязательный параметр; компилятор не позволит забыть
// CanSellerManageAuction вызывается внутри updateFn или до неё
```

На что смотреть: `actor` стоит в сигнатуре `Update` — хендлер, «забывший» про авторизацию, не скомпилируется. Для системных потоков — отдельный метод с говорящим именем `UpdateAsSystem`, а не `Update` с `actor = fakeAdminUser`: в аудит-логе системные операции выглядят как системные, а не как один подозрительно трудолюбивый администратор. (Глава 13.)

## Группа 9. Бизнес-if в app-слое

**Как выглядит.** Хендлер use case обзаводится бизнес-ветвлением: `if amount > 10000 && !bidder.IsVerified()` прямо в `Handle`. Заодно use case начинает возвращать HTTP-статусы: `return 409, ErrBidBelowMinimum`. Где-то рядом app-пакет уже импортирует адаптеры напрямую.

```go
// — антипример
func (h PlaceBidHandler) Handle(ctx context.Context, cmd PlaceBid) (int, error) {
    if cmd.Amount > 10000 && !cmd.BidderVerified {
        return 403, errors.New("verification required") // статус из домена — неправильно
    }
    // ...
}
```

На что смотреть: число `10000` и статус `403` в одной функции. Первое — бизнес-правило, второе — деталь транспорта; app-слою не принадлежит ни то, ни другое.

**Чем кончается через полгода.** Правило «ставки выше порога требуют верификации» существует в двух-трёх экземплярах: в хендлере, возможно в домене, и ещё разок в тесте. Порог поменяли в одном месте — забыли в другом, и какое-то время система применяет два порога одновременно. А HTTP-статус из use case означает, что use case знает про HTTP, — при появлении gRPC-порта это знание придётся выкорчёвывать.

**Как правильно.** Бизнес-`if`, замеченный в app-слое, — формальный признак протечки, и решение всегда одно: он переезжает в домен. App-слой — чистая оркестрация. Ошибки — ports-agnostic slugs, транслируются в статусы в портах.

```go
// internal/auction/domain/auction/auction.go — правило в домене
if !b.Verified() {
    needsVerification, err := amount.GTE(a.verifyAbove)
    if err != nil || needsVerification {
        return Bid{}, ErrVerificationRequired
    }
}

// internal/auction/app/command/place_bid.go — app только оркестрирует
func (h PlaceBidHandler) Handle(ctx context.Context, cmd PlaceBid) error {
    // ... никакого бизнес-if; вся логика внутри a.PlaceBid(...)
}

// internal/auction/app/command/place_bid.go — маппинг ошибок в слаги
case errors.Is(err, auction.ErrVerificationRequired):
    return errs.NewForbiddenError("verification-required").WithCause(err)
```

На что смотреть: домен решает, app передаёт, порт переводит ошибку на язык транспорта — и эта цепочка выдерживает добавление любого нового порта. (Глава 4, глава 7.)

## Группа 10. Микросервисы как лекарство от сложности

**Как выглядит.** «Монолит стал большим — режем на микросервисы». Нарезка по существительным (UserService, AuctionService) или по экранам. Каждая бизнес-фича требует изменений в трёх сервисах и их синхронного деплоя. На фоне звучит «Kubernetes решит проблемы дизайна» — фраза для коллекции.

**Чем кончается через полгода.** Distributed monolith: та же связность, плюс сетевые вызовы, плюс версионирование API между командами, плюс distributed transactions (или их отсутствие — с потерей консистентности), плюс зоопарк инфраструктуры. Худшее из обоих миров. DORA-исследования говорят прямо: loose coupling достигается хорошим дизайном, а не микросервисами. Разрезав плохо спроектированный монолит, вы получите плохо спроектированную распределённую систему — швы те же, но теперь по ним ходит сеть.

**Как правильно.** Сначала — правильные границы: из доменного анализа, строгие (`internal/` + lint в CI), с общением только через события и фасады. Когда контекст фактически потребует независимого деплоя или масштаба — он вынесется легко, потому что его границы уже автономны. В Molot: пять bounded contexts в одном бинаре, каждый со своей схемой и версионированными событиями. Вынести `billing` в отдельный сервис — замена одного адаптера, не переписывание (рецепт — в главе 17).

```
internal/
    auction/   — своя схема, свои events/, свои миграции
    billing/   — то же
    settlement/
    participant/
    notification/
```

На что смотреть: каждый контекст уже выглядит как сервис — своя схема, свои события, свои миграции. Просто пока все живут в одном процессе, и это «пока» ничего не стоит. (Глава 1, глава 2.)

## Группа 11. Тактический DDD без стратегического

**Как выглядит.** Entity, Repository, Value Object — есть, всё по учебнику. Event Storming — нет. Границы нарезаны «по похожести сущностей»: `Invoice` и `Auction` в одном модуле, потому что «оба про деньги». Стейкхолдеры узнают границы по факту — когда менять уже дорого. Это как выучить грамматику языка без единого слова: формы безупречны, сказать нечего.

**Чем кончается через полгода.** Неправильная граница — та, которую приходится пересекать на каждой новой фиче. «Добавить второй шанс бидеру» затрагивает auction, billing, settlement и notification одновременно — не потому что задача сложная, а потому что границы проведены не там. Команда делает вывод «DDD не работает», хотя стратегическую часть никто не пробовал. Литмус-тест: если новая фича не помещается в один модуль — граница неправильная.

**Как правильно.** Стратегический DDD первым: доменный поток (аналог Event Storming), артефакт хранится в репо, границы — там, где меняется ответственность и язык. Потом тактика. В Molot: `settlement` существует отдельно от `auction` именно потому, что «расчёт после молотка» — отдельная ответственность с отдельным языком (settlement, compensation, second-chance) и отдельным темпом изменений. (Глава 2.)

## Группа 12. BDUF и код «на будущее»

**Как выглядит.** «Нам потом понадобится event sourcing — заложим сейчас». Месячные refactoring-ветки без мержа в main. «Нужно было сделать правильно с самого начала» — и пишется фреймворк вместо продукта. Или зеркальный перфекционизм: «пока пишем, всё равно всё изменится» — и не пишется ничего, кроме абстракций.

**Чем кончается через полгода.** Бюджет изменений — время и внимание команды — потрачен на задачи, которые не наступили. Долгоживущие ветки протухают: конфликты, потерянный контекст, ревью на четыреста файлов, которое никто честно не прочитает. «Код на будущее» — кредит под сложность: проценты платите сегодня, а сам займ, скорее всего, не пригодится никогда.

**Как правильно.** MVP-инкременты. Код «на будущее» отклоняется — вместо него дизайн, в котором будущее легко добавить. В Molot отдельного read store нет — читаем из той же БД. Когда понадобится — встанет заменой адаптера: query handler объявляет интерфейс `AvailableAuctionsReadModel`, а откуда данные — скрыто за этим интерфейсом.

```go
// internal/auction/app/query/active_catalog.go
// Query handler объявляет интерфейс у себя — реализация меняется без касания этого файла
type ActiveCatalogReadModel interface {
    ActiveAuctions(ctx context.Context, q ActiveCatalog) ([]AuctionSummary, error)
}
```

На что смотреть: это вся «подготовка к будущему» — один интерфейс, объявленный там, где используется. Elasticsearch-кода нет ни строчки, но день, когда он понадобится, обойдётся в одну новую реализацию. (Глава 15, глава 14.)

## Группа 13. Тестовые грехи

Восемь грехов — и у каждого было оправдание, звучавшее разумно в момент коммита.

**Ice-cream cone (e2e как основа).** Большинство тестов — end-to-end, unit-тестов мало. Каждый прогон — 20 минут, каждый второй флакает на сети. Кончается тем, что команда перестаёт запускать тесты локально, — а тест, который не запускают, защищает как сигнализация с вынутой батарейкой. *Правильно:* пирамида — домен unit без инфраструктуры, e2e — пара critical paths.

**Тесты вне CI.** «Пока не настроили CI — запускаем руками». Через две недели не запускает никто: ручная дисциплина масштабируется ровно до первого дедлайна. *Правильно:* merge-gate с первого дня.

**`sleep` и растущие ретраи как лечение флаков.** `time.Sleep(100 * time.Millisecond)` в тесте — признание, что тест не знает, когда система готова. Следующий разработчик увидит флак и увеличит sleep до 500ms — сьют медленно превращается в коллекцию пауз. *Правильно:* `assert.Eventually` или синхронизация каналами.

**Cleanup данных между тестами.** `defer cleanupDB()` означает, что тест зависит от порядка выполнения, — а в параллельных тестах cleanup радостно убивает данные соседнего теста. *Правильно:* изоляция уникальными ID, никогда не чистим.

**Тестирование мока.** `assert.Equal(t, 1, mock.CallCount())` проверяет, что мок был вызван. Что система работает правильно — не проверяет: это тест, который проверяет сам себя. *Правильно:* тест проверяет наблюдаемый эффект, а не внутреннюю механику.

**Loop-var capture в `t.Parallel()`.** Классическая Go-ловушка: все итерации замыкания захватывают одну и ту же переменную. Тесты зелёные — и прогоняют один и тот же case восемь раз. *Правильно:* `c := testCases[i]` внутри цикла (или Go 1.22+).

**100%-coverage как цель.** Карго-культ: каждая строка исполнена, ни один инвариант не проверен. *Правильно:* 70–80% для Go — хорошо; критерий — «насколько легко сломать то, что охраняет тест».

**Тесты-зеркала реализации.** Тест проверяет: «метод вызвал именно эти методы в именно таком порядке». Рефакторинг без изменения поведения — сотня упавших тестов, и команда начинает бояться рефакторинга. *Правильно:* тест проверяет поведение через публичный API.

В Molot: `t.Parallel()` везде, изоляция UUID, обязательный rollback-тест и race-тест (20 горутин, один победитель), `-race` в `make test`, один shared suite на Postgres и in-memory. (Глава 11.)

**Нюанс.** `sleep` в тесте опасен не тем, что замедляет сьют, а тем, что лечит симптом. Если тесту нужно «подождать готовности», а способа узнать о ней нет — этого способа нет и у production-кода. Флак — часто не болезнь теста, а честный репортаж о гонке, которая воспроизведётся под нагрузкой. Прежде чем увеличивать паузу, спросите: что в проде играет роль этого sleep?

## Группа 14. Вера в то, что строгий контракт гарантирует качество данных

**Как выглядит.** «Используем gRPC/protobuf — значит данные всегда корректны». Валидация заканчивается на том, что поле `string` не nil. И по системе начинают ходить безупречно сериализованные бессмысленные значения: `amount = 0`, `currency = ""`, `bidder_id = "undefined"`.

**Чем кончается через полгода.** Строгий контракт гарантирует ровно одно: данные правильно сериализованы. Типы сошлись — смысл никто не проверял. `amount = 0` пройдёт через gRPC без единого предупреждения и создаст ставку на ноль рублей — если домен не отклонит. Через полгода база полна «правильно оформленного» мусора, и каждый отчёт начинается с `WHERE amount > 0` — молчаливого памятника этой вере.

**Как правильно.** Три слоя валидации, у каждого своя зона: контракт (proto constraints / OpenAPI validation) — форма; contract tests (потребитель проверяет, что продюсер держит обещания) — совместимость; доменные инварианты (валидирующий конструктор) — смысл. В Molot: конструктор `New(...)` отклоняет нулевые amount, пустые ID, некорректные currency — каким бы транспортом данные ни приехали.

```go
// internal/auction/domain/auction/auction.go
func New(..., startPrice, increment Money, ...) (*Auction, error) {
    if startPrice.IsZero() || startPrice.AmountMinor() <= 0 {
        return nil, ErrInvalidStartPrice
    }
    if startPrice.Currency() != rules.Currency() {
        return nil, ErrUnsupportedCurrency
    }
    // ...
}
```

На что смотреть: конструктору всё равно, пришли данные из gRPC, HTTP или теста, — последний рубеж один для всех входов. (Глава 4, глава 6.)

## Группа 15. Самописная аутентификация

**Как выглядит.** Собственное хэширование паролей (`md5(password + "salt")`), собственная генерация токенов, собственный протокол сессий. Рядом — «временный» хардкод пароля администратора для тестирования. Слово «временный» здесь значит примерно то же, что «временные» бытовки у долгостроя.

**Чем кончается через полгода.** OWASP Top 10 #2 — Cryptographic Failures. Самописная крипто неизбежно содержит уязвимости, и найдёт их не penetration-тест, а злоумышленник в production. «Временный» бэкдор переживает три рефакторинга и остаётся навсегда. Дело не в компетентности: криптографические ошибки требуют экспертизы, которой нет у большинства команд, — и растить её ради велосипеда странно.

**Как правильно.** Стандартный JWT с библиотекой, один middleware, всё, что сложнее, — провайдер (Auth0, Keycloak, AWS Cognito). В Molot: `golang-jwt/jwt` с HS256, `NewMiddleware` принимает режим из конфига и явно отклоняет неизвестные режимы с actionable-ошибкой.

```go
// internal/common/auth/auth.go
func NewMiddleware(mode, hs256Secret string) (func(http.Handler) http.Handler, error) {
    switch mode {
    case ModeLocalHS256:
        if hs256Secret == "" {
            return nil, errors.New("auth: AUTH_HS256_SECRET must not be empty when AUTH_MODE=local-hs256")
        }
        return hs256Middleware([]byte(hs256Secret)), nil
    case ModeJWKS:
        return nil, errors.New("auth: AUTH_MODE=jwks is not implemented yet: run with AUTH_MODE=local-hs256 ...")
    default:
        return nil, fmt.Errorf("auth: unknown AUTH_MODE %q", mode)
    }
}
```

На что смотреть: middleware отказывается стартовать с пустым секретом и молча принять неизвестный режим. Ошибка конфигурации обнаруживается при старте процесса, а не при первом токене в проде. (Глава 13.)

## Группа 16. Срезание углов как привычка и его зеркало — over-engineering

Это два полюса одной ошибки — неумения соизмерять усилие со сложностью задачи, — и разрушительны они одинаково.

**Срезание углов как привычка.** Не осознанное прагматичное решение («у нас MVP, вернёмся через спринт»), а рефлекс. Отсутствие тестов, прямая мутация полей агрегата, `TODO: fix this properly`, транзакция через context — не потому что «сейчас некогда», а потому что «и так сойдёт». Разница диагностируется просто: у осознанного shortcut-а есть запись, автор и дата возврата. У рефлекса нет ничего — это просто стиль.

**Чем кончается через полгода.** Команда боится менять код: каждая правка ломает что-то в соседней комнате. Тест-сьют красный уже два месяца, и никто не помнит почему. Новый разработчик не может понять, что здесь «правильно», — примеров правильного нет, и он, человек разумный, копирует то, что видит. Так привычка становится культурой.

**Over-engineering — симметричная ошибка.** Полный DDD-стек на CRUD-модуль для хранения email-адресов. Event sourcing, потому что «звучит серьёзно». Командная шина внутри монолита. Шесть уровней абстракции для `SELECT * FROM users WHERE id = ?`. Бюджет изменений уходит на борьбу с собственной архитектурой — бизнес-задачи подождут.

**Как правильно.** Паттерн применяется пропорционально сложности того, что он защищает. Исключение документируется и пересматривается при росте логики. В Molot: `notification` — без domain/app слоёв: событие → шаблон → отправка; `participant` — слои есть, но без проекций. Исключение написано прямо в пакете:

```go
// internal/notification/service/service.go
// Package service is the composition root of the notification context:
// it wires the fake email sender and the Postgres stores into the event
// handlers... The context has no HTTP API and no facade — it is a pure
// event consumer.

// internal/participant/service/service.go
// The context publishes ParticipantRegisteredV1/ParticipantVerifiedV1
// and subscribes to nothing, so there is no RegisterEventHandlers;
// no other context calls participant synchronously, so there is no Facade.
```

На что смотреть: оба комментария не извиняются, а объясняют — почему слоёв нет и при каких условиях они не нужны. Это и отличает осознанное упрощение от срезанного угла. (Глава 14.)

**Совет из практики.** Исключение живёт рядом с кодом и содержит условие пересмотра: не «тут всё просто», а «здесь нет app-слоя, потому что контекст — чистый консьюмер событий; появится HTTP API — слой добавить». Такое исключение само сообщает, когда перестанет быть верным; исключение без условия пересмотра — срезанный угол с хорошей самооценкой.

## Чек-лист самопроверки

Перед code review пройдитесь по списку. Каждый «да» — ещё не приговор, а повод для разговора с командой; больше трёх «да» — разговор не откладывать.

**Модель**
- [ ] Есть публичные поля или сеттеры на доменном типе?
- [ ] Бизнес-`if` в хендлере или app-слое (не в домене)?
- [ ] Состояние кодируется строками или булевыми парами вместо value objects?
- [ ] Конструктор без валидации или с частичной валидацией?

**Слои**
- [ ] `db:` или `json:` теги на доменном типе?
- [ ] Один struct используется и для хранения, и для API?
- [ ] App-пакет импортирует адаптеры?
- [ ] HTTP-статус возвращается из use case или домена?

**Репозиторий и транзакции**
- [ ] Транзакция в `context.Value` или прокидывается через параметры?
- [ ] `updateFn` мутирует переданный указатель вместо возврата нового значения?
- [ ] Нет `SELECT ... FOR UPDATE` при read-modify-write?
- [ ] Репозиторий содержит бизнес-правила или валидацию?
- [ ] В интерфейсе repo есть per-use-case методы?

**Безопасность**
- [ ] Авторизация — ручные `if` в хендлерах?
- [ ] Системные потоки используют fake user с нужными правами?
- [ ] Identity берётся из `context.Value` внутри repo?
- [ ] Самописная крипто или хардкод секретов?

**Тесты**
- [ ] Большинство тестов — e2e (перевёрнутая пирамида)?
- [ ] `sleep` в тестах?
- [ ] Cleanup данных между тестами?
- [ ] Тест проверяет, что мок был вызван, а не наблюдаемый эффект?
- [ ] Loop-var без копирования в `t.Parallel()`?

**Архитектура**
- [ ] Новая фича открывает больше одного модуля?
- [ ] Микросервисы создаются до понимания доменных границ?
- [ ] Добавлен код «на будущее» без конкретной потребности?
